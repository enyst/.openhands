# Validate Idea

Test before you build. Talk to people, not code.

## When to use

You have a community and a pain point. Before writing any code, validate that people will pay for a solution.

## The principle

The goal is not to build something and see if people want it. The goal is to find out what people want and then build it. Validation is a conversation, not a launch.

## How to apply

1. **Talk to 10-20 people in your community.** Not a survey — actual conversations. Ask:
   - "What's the hardest part of [the thing]?"
   - "How do you solve it now?"
   - "What have you tried?"
   - "Would you pay for something that [does X]?" (Don't describe your solution — describe the outcome)

2. **Look for patterns.** If 7 out of 10 people describe the same pain, you have something. If everyone describes a different problem, go back to find-community.

3. **Pre-sell it.** Before building anything:
   - Describe the solution in one sentence
   - Ask: "If this existed today, would you buy it for $X?"
   - If yes: "Can I charge you now and deliver it in [timeframe]?"
   - Goal: get 3-5 paying customers before you write a line of code

4. **Define the smallest thing that solves the core pain.** Not the product vision — the first thing you could ship in a weekend that makes one person's life better.

## Output

A validation document with:
- Number of conversations and key quotes
- The pattern: what pain came up repeatedly
- Pre-sale results (how many said yes, how many paid)
- The one-sentence solution description
- The weekend-sized MVP scope

## Anti-patterns

- Building first, validating later ("if I build it they will come")
- Asking friends/family who'll say yes to be nice
- Asking "would you use this?" instead of "would you pay for this?"
- Confusing interest with willingness to pay
